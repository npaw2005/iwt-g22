1. Viva Strategy & Examiner Psychology

Strategic MindsetExaminer Evaluation Rubric

In a project viva, the examiner is NOT evaluating whether your system has flashy graphics. They are evaluating four core competencies:

  1. Code Ownership & Authorship: Did you write this code yourself? Can you explain any arbitrary line selected by the examiner without hesitation?
  2. Data Flow Understanding: Can you trace the exact journey of a variable from an HTML form through JavaScript, across HTTP headers, into PHP superglobals, down into MySQL disk storage, and back?
  3. Architectural & Security Justifications: Can you defend why you used PDO instead of raw queries, why 3NF was chosen, and how you stopped SQL Injection and XSS?
  4. Live Coding Agility: Can you open the source code in your editor and perform a live modification requested by the examiner within 60 seconds?

2. End-to-End System Request Lifecycle

Architecture WalkthroughFrom Click to Database Storage

When the examiner asks: "Walk me through what happens when a student clicks 'Submit Application'," recite this exact 6-phase sequence:

  1. Phase 1: DOM Event Interception (JavaScript): In public/home.php line 113, the form's onsubmit="return checkApplication()" catches the submission event. Lines 292-353 run client-side validation (non-empty fields, date not in future, 12-digit numeric NIC loop, GPA between 0.00 and 4.00, testimonial checkbox). If invalid, an alert() appears and JS returns false, aborting the HTTP request.
  2. Phase 2: HTTP POST Transmission: If valid, JS returns true. The browser serializes all named inputs into an HTTP POST request body and dispatches it across TCP/IP to Apache HTTPD on port 80.
  3. Phase 3: Server & Session Authentication: Apache delegates the request to the PHP interpreter. In lines 2-3, session_start() reads the client's PHPSESSID cookie and verifies that $_SESSION['role'] === 'student'. require_once '../config/db.php' establishes the PDO connection.
  4. Phase 4: Duplicate Application Check: In lines 36-38, PHP checks if this student has already applied for this scholarship using: $check = $conn->prepare("SELECT COUNT(*) FROM student_scholarships WHERE student_id = ? AND scholarship_id = ?");. If count > 0, submission halts.
  5. Phase 5: Atomic Relational Database Persistence: Lines 48-53 update or insert the student's profile into the students table. Line 55 inserts the application record into the student_scholarships junction table using a prepared statement with bound parameters.
  6. Phase 6: HTML View Synthesis: PHP queries the updated records, wraps dynamic values in htmlspecialchars(), applies style.css, and sends the rendered HTML back to the browser for layout and painting.

3. Top 20 Examiner Defense Questions & Model Answers

Viva Question 1 (Crucial!)Read-only Database Flow

Examiner: "How do you fetch information from the database and make it visible in the form as readonly?"

Candidate Answer:
"We achieve this in four steps in public/home.php:
1. In lines 73-75, when a logged-in student accesses the form, we query their existing bio-data from MySQL using PDO: $profStmt = $conn->prepare("SELECT ... FROM students WHERE user_id = ?"); $profStmt->execute([$_SESSION['user_id']]);.
2. We fetch the returned row into an associative array: $userProfile = $profStmt->fetch();.
3. In the HTML form line 121, we echo the database value directly inside the input's value attribute: value="<?php echo htmlspecialchars($username); ?>".
4. Finally, we append the boolean HTML attribute readonly (and our CSS class input-readonly). This ensures the user cannot edit the field, while guaranteeing that the value is still submitted in the HTTP POST payload (unlike the disabled attribute which omits the field from transmission)."

Viva Question 2Security Architecture

Examiner: "What is SQL Injection, and how does your codebase prevent it?"

Candidate Answer:
"SQL Injection occurs when user input is concatenated directly into an SQL string (e.g. WHERE user = '$u'). An attacker entering ' OR '1'='1 alters query logic to bypass authentication.
In our project, we completely eliminated this across all files (e.g. public/login.php line 19, public/admin.php line 23) by exclusively using PDO Prepared Statements with parameter markers (?). The database pre-compiles the SQL query template first. When user inputs are supplied via execute([$username]), the database engine treats them strictly as passive data, rendering SQL injection mathematically impossible."

Viva Question 3Security Architecture

Examiner: "What is Cross-Site Scripting (XSS), and where did you protect against it?"

Candidate Answer:
"XSS occurs when malicious scripts entered by a user (e.g. <script>steal()</script>) are rendered by the server directly into the HTML of other users, executing in their browser context.
We prevent this by wrapping every dynamic database output in htmlspecialchars() (e.g. in public/admin.php line 174 and public/applications.php line 69). This converts <, >, &, and " into safe HTML entities, forcing the browser to render strings harmlessly as plain text."

Viva Question 4State Management

Examiner: "Why did you use session_start() at the top of every page, and how does your Role-Based Access Control (RBAC) work?"

Candidate Answer:
"Because HTTP is stateless, the server forgets client identity between requests. Calling session_start() reads the client's PHPSESSID cookie and restores the server-side $_SESSION array.
During login in public/login.php lines 24-26, we store $_SESSION['user_id'] and $_SESSION['role'].
In protected administrative files like public/admin.php lines 5-8 and public/applications.php lines 5-8, we check: if (!isset($_SESSION['user_id']) || $_SESSION['role'] !== 'admin') { header('Location: home.php'); exit(); }.
If an unauthorized user attempts to access the admin URL directly, they are redirected and script execution halts via exit()."

Viva Question 5Database Design

Examiner: "Explain your database normalization. How does your schema satisfy Third Normal Form (3NF)?"

Candidate Answer:
"Our schema in schema.sql is decomposed into 4 relations satisfying 3NF:
1. 1NF: All attributes contain atomic values; there are no multivalued columns or repeating groups.
2. 2NF: In the junction table student_scholarships, the composite primary key is (student_id, scholarship_id). All descriptive attributes (e.g. purpose, status) functionally depend on the complete composite key, eliminating partial dependencies.
3. 3NF: We eliminated transitive dependencies by creating a separate students profile table linked via foreign key to users. Student bio-data (address, NIC, parents income) depends solely on user_id and does not pollute the users authentication table or the scholarships definition table."

Viva Question 6schema.sql Line 46

Examiner: "What happens to student applications when a scholarship is deleted by the registrar?"

Candidate Answer:
"They are automatically deleted by the MySQL InnoDB engine. In schema.sql line 46, when defining the student_scholarships foreign key, we specified FOREIGN KEY (scholarship_id) REFERENCES scholarships(id) ON DELETE CASCADE. This guarantees referential integrity and prevents orphan child records."

Viva Question 7public/applications.php Line 41

Examiner: "Explain how your 4-table join works. Why did you use a LEFT JOIN for students instead of an INNER JOIN?"

Candidate Answer:
"In line 41 of public/applications.php, we join student_scholarships with users, students, and scholarships.
We deliberately used a LEFT JOIN for students because if a newly registered student submits an application before completing every optional field in their student profile, an INNER JOIN would completely exclude and hide that application from the Registrar's dashboard! The LEFT JOIN ensures the application is always visible, displaying NULL for any uncompleted profile attributes."

Viva Question 8public/admin.php Line 52

Examiner: "What safety checks prevent an administrator from deleting another administrator or locking the system?"

Candidate Answer:
"In public/admin.php lines 49-57, before executing any deletion query, we first query the user's role from the database: $check = $conn->prepare("SELECT role FROM users WHERE id = ?"); $check->execute([$id]); $u = $check->fetch();
We then explicitly check: if ($u && $u['role'] !== 'admin'). If the target user is an administrator, the delete query is rejected and the system displays an alert: 'Cannot delete admin accounts.'"

Viva Question 9Client-Side Architecture

Examiner: "Why is the return keyword compulsory in <form onsubmit='return checkApplication()'>?"

Candidate Answer:
"The inline onsubmit attribute expects an expression evaluating to a boolean that determines whether the browser's default form submission event should proceed. If you write onsubmit='checkApplication()' without return, the function executes and returns false, but the onsubmit handler itself returns undefined, which the browser treats as truthy and submits the form anyway! Writing return checkApplication() passes the boolean false directly to the browser, successfully cancelling the submission event."

Viva Question 10JavaScript Algorithms

Examiner: "Why did you validate NIC numbers and dates using loops and character comparisons instead of regular expressions?"

Candidate Answer:
"In our course syllabus (IS1207), students are taught fundamental algorithmic string inspection using length, charAt(), indexOf(), and split() to demonstrate core procedural logic rather than delegating validation to regex engines. In public/home.php lines 334-339, we verify each character with if (nic.charAt(i) < '0' || nic.charAt(i) > '9'), strictly satisfying course guidelines."

Live Task 3Adding an SQL Filter

Examiner Instruction: "Modify the Registrar view in applications.php to only show 'pending' applications."

Exact Code Action: Open public/applications.php line 41. Locate the SQL query and append WHERE ss.status = 'pending' right before ORDER BY: 

$stmt = $conn->query("SELECT ss.*, u.username, ... 
    FROM student_scholarships ss 
    INNER JOIN users u ON ss.student_id = u.id 
    LEFT JOIN students st ON u.id = st.user_id 
    INNER JOIN scholarships s ON ss.scholarship_id = s.id 
    WHERE ss.status = 'pending' 
    ORDER BY ss.applied_at DESC");
