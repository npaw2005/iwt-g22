1. Viva Strategy & Examiner Psychology

Strategic Mindset What Examiners Are Testing

In a project viva, the examiner is NOT merely checking if your web system works. They are rigorously verifying code ownership, architectural understanding, and security awareness:

  • Authenticity & Code Ownership: Did you write this code yourself, or did someone else do it? Examiners test this by pointing to a specific line and asking, "Why did you write this here?" or asking you to make a live change on the spot.
  • Data Flow Understanding: Can you explain how data travels from an HTML form element through the JavaScript event layer, across the HTTP network payload, into PHP superglobals, and down to MySQL disk storage?
  • Security & Vulnerability Defenses: Do you know why raw queries are dangerous (SQL Injection) and why unescaped strings in HTML are dangerous (XSS)?
  • The Golden Rule: Never answer with "It just worked" or "I found it online". Always state the architectural principle (e.g. "We used PDO prepared statements to decouple the SQL command structure from user data, guaranteeing mathematical immunity from SQL injection attacks").

2. Complete System Request Lifecycle

End-to-End Trace From Browser Click to MySQL Execution

When an examiner asks: "Walk me through what happens when a student clicks 'Submit Application' in your project," give this exact 6-step breakdown:

  1. Client Event Interception (DOM Level 0):
    In public/home.php line 113, the form's onsubmit="return checkApplication()" intercepts the click. The browser executes JavaScript.
    Lines 292-353 validate all fields (non-empty name, date of birth not in the future, 12-digit numeric NIC check, GPA between 0.00 and 4.00, and testimonial checkbox checked).
    If any condition fails, an alert() is displayed and JS returns false, aborting the HTTP request.
  2. HTTP POST Transmission:
    If JS returns true, the browser serializes all named input values into an HTTP POST payload and dispatches an HTTP request to home.php.
  3. Server Execution & Session Authentication:
    Apache receives the request and invokes the PHP engine.
    In lines 2-3, session_start() loads the student's authenticated user ID, and require_once '../config/db.php' establishes the persistent PDO database connection.
  4. Duplicate Check (Business Logic):
    In lines 36-38, PHP checks if this student has already applied for this scholarship: $check = $conn->prepare("SELECT COUNT(*) FROM student_scholarships WHERE student_id = ? AND scholarship_id = ?");.
    If count > 0, an alert is set and submission halts.
  5. Atomic Database Persistence:
    If valid, lines 48-53 update or insert the student's personal profile into the students table.
    Then line 55 inserts the application record into the student_scholarships table using a prepared statement with bound parameters.
  6. Dynamic Response Generation:
    PHP queries the updated applications table, renders the HTML markup with the new record, applies the external CSS stylesheet, and sends the rendered HTML back to the browser.

3. Top 20 Examiner Defense Questions & Model Answers

Viva Question 1 (Crucial!) public/home.php Lines 73-82 & 121

Examiner: "How do you get information from the database and make it visible in the form as readonly?"

Model Answer:
"We achieve this in four distinct steps in public/home.php:
1. In lines 73-75, when a logged-in student opens the application form, we query their existing bio-data from MySQL using PDO: $profStmt = $conn->prepare("SELECT ... FROM students WHERE user_id = ?"); $profStmt->execute([$_SESSION['user_id']]);
2. We extract the returned record into an associative array: $userProfile = $profStmt->fetch();.
3. In the HTML form line 121, we echo the database value directly inside the input's value attribute: value="<?php echo htmlspecialchars($username); ?>".
4. Finally, we append the boolean HTML attribute readonly (and our CSS class input-readonly). This ensures the user cannot edit their username, while guaranteeing that the value is still submitted in the HTTP POST payload (unlike the disabled attribute which omits the field from transmission)."

Viva Question 2 Security Architecture

Examiner: "What is SQL Injection, and how does your codebase prevent it?"

Model Answer:
"SQL Injection occurs when untrusted user input is concatenated directly into an SQL string (e.g. SELECT * FROM users WHERE user = '$u' AND pass = '$p'). An attacker entering ' OR '1'='1 can hijack the query logic to bypass authentication or drop tables.
In our project, we completely eliminated this vulnerability across all files (e.g. public/login.php line 19, public/admin.php line 23) by exclusively using PDO Prepared Statements with parameter markers (?). The database pre-compiles the SQL query template first. When user inputs are supplied via execute([$username]), the database treats them strictly as passive data, rendering malicious SQL code execution impossible."

Viva Question 3 Security Architecture

Examiner: "What is Cross-Site Scripting (XSS), and where in your codebase did you protect against it?"

Model Answer:
"Cross-Site Scripting (XSS) occurs when malicious JavaScript code entered by a user (e.g. in a name or description field: <script>stealCookies()</script>) is rendered by the server directly into the HTML page of other users, executing in their browser context.
We prevent this by wrapping every dynamic database output in htmlspecialchars() (e.g. in public/admin.php line 174 and public/applications.php line 69). This sanitizes special HTML characters: < becomes &lt;, > becomes &gt;, and & becomes &amp;. The browser safely prints the string as harmless visible text instead of executing it as markup."

Viva Question 4 State Management

Examiner: "Why did you use session_start() at the top of every page, and how does your Role-Based Access Control (RBAC) work?"

Model Answer:
"Because HTTP is inherently stateless, the server forgets who the client is between requests. Calling session_start() reads the client's PHPSESSID cookie and restores the server-side $_SESSION array.
During login in public/login.php lines 24-26, upon successful password verification, we store $_SESSION['user_id'] and $_SESSION['role'].
In protected administrative files like public/admin.php lines 5-8 and public/applications.php lines 5-8, we check: if (!isset($_SESSION['user_id']) || $_SESSION['role'] !== 'admin') { header('Location: home.php'); exit(); }.
If a student or unauthenticated guest attempts to access the admin URL directly, they are instantly redirected and execution halts via exit()."

Viva Question 5 Database Design & Normalization

Examiner: "Explain your database normalization. How does your schema satisfy Third Normal Form (3NF)?"

Model Answer:
"Our schema in schema.sql is decomposed into 4 relations satisfying 3NF:
1. 1NF: All attributes contain atomic values; there are no multivalued columns or repeating groups.
2. 2NF: In the junction table student_scholarships, the composite primary key is (student_id, scholarship_id). All descriptive attributes (e.g. purpose, status) functionally depend on the complete composite key, eliminating partial dependencies.
3. 3NF: We eliminated transitive dependencies by creating a separate students profile table linked via foreign key to users. Student bio-data (address, NIC, parents income) depends solely on user_id and does not pollute the users authentication table or the scholarships definition table."

Viva Question 6 schema.sql Lines 45-46

Examiner: "What happens to student applications when a scholarship is deleted by the registrar?"

Model Answer:
"They are automatically deleted by the MySQL InnoDB engine. In schema.sql line 46, when defining the student_scholarships foreign key, we specified FOREIGN KEY (scholarship_id) REFERENCES scholarships(id) ON DELETE CASCADE. This guarantees referential integrity and prevents orphan child records from cluttering the database."

Viva Question 7 public/applications.php Line 41

Examiner: "Explain how your 4-table join works in applications.php. Why did you use a LEFT JOIN for the students table instead of an INNER JOIN?"

Model Answer:
"In line 41 of public/applications.php, we join student_scholarships with users, students, and scholarships.
We deliberately used a LEFT JOIN for students because if a newly registered student submits an application before completing every optional field in their student profile, an INNER JOIN would completely exclude and hide that application from the Registrar's dashboard! The LEFT JOIN ensures the application is always visible, displaying NULL for any uncompleted profile attributes."

Viva Question 8 public/admin.php Line 52

Examiner: "What safety checks prevent an administrator from deleting another administrator or locking the system?"

Model Answer:
"In public/admin.php lines 49-57, before executing any deletion query, we first query the user's role from the database: $check = $conn->prepare("SELECT role FROM users WHERE id = ?"); $check->execute([$id]); $u = $check->fetch();
We then explicitly check: if ($u && $u['role'] !== 'admin'). If the target user is an administrator, the delete query is rejected and the system displays an alert: 'Cannot delete admin accounts.'"

Viva Question 9 Client-Side Architecture

Examiner: "Why is the return keyword compulsory in <form onsubmit='return checkApplication()'>?"

Model Answer:
"The inline onsubmit attribute expects an expression evaluating to a boolean that determines whether the browser's default form submission event should proceed. If you write onsubmit='checkApplication()' without return, the function executes and returns false, but the onsubmit handler itself returns undefined, which the browser treats as truthy and submits the form anyway! Writing return checkApplication() passes the boolean false directly to the browser, successfully cancelling the submission event."

Viva Question 10 JavaScript Algorithms

Examiner: "Why did you validate NIC numbers and dates using loops and character comparisons instead of regular expressions?"

Model Answer:
"In our course syllabus (IS1207), students are taught fundamental algorithmic string inspection using length, charAt(), indexOf(), and split() to demonstrate core procedural logic rather than delegating validation to regex engines. In public/home.php lines 334-339, we verify each character with if (nic.charAt(i) < '0' || nic.charAt(i) > '9'), strictly satisfying course guidelines."

4. Live Coding Defense Challenges (On-the-Spot Tasks)

Live Task 1 Making a Field Read-Only

Examiner Instruction: "Open public/home.php and make the student's NIC field read-only right now."

Exact Code Action: Navigate to line 150 of public/home.php. Change: 

<!-- BEFORE -->
<input type="text" name="nic" value="<?php echo htmlspecialchars($userProfile['nic']); ?>">

<!-- AFTER (Add readonly attribute & input-readonly class) -->
<input type="text" name="nic" value="<?php echo htmlspecialchars($userProfile['nic']); ?>" class="input-readonly" readonly>
Save the file, refresh the browser, and demonstrate to the examiner that the field is now greyed out and cannot be edited, but will still submit to PHP on POST!

Live Task 2 Adding a Confirmation Dialog

Examiner Instruction: "Add a confirmation prompt before a student submits their application."

Exact Code Action: Navigate to line 113 of public/home.php or the submit button. In checkApplication() line 352, change: 

// In checkApplication() right before 'return true;'
if (!confirm("Are you sure you want to submit this application? You cannot edit it later.")) {
    return false;
}
return true;
Save and test in the browser.

Live Task 3 Adding an SQL Filter

Examiner Instruction: "Modify the Registrar view in applications.php to only show 'pending' applications."

Exact Code Action: Open public/applications.php line 41. Locate the SQL query and append WHERE ss.status = 'pending' right before ORDER BY: 

// Line 41 in public/applications.php
$stmt = $conn->query("SELECT ss.*, u.username, ... 
    FROM student_scholarships ss 
    INNER JOIN users u ON ss.student_id = u.id 
    LEFT JOIN students st ON u.id = st.user_id 
    INNER JOIN scholarships s ON ss.scholarship_id = s.id 
    WHERE ss.status = 'pending' 
    ORDER BY ss.applied_at DESC");
Save and refresh.
