Detailed Code & Expression BreakdownLines 1-8
  • Line 1 (<?php): Opening PHP delimiter tag. Instructs the Apache Zend Engine parser to interpret following tokens as server-side PHP instructions rather than sending raw text to the HTTP output stream.
  • Line 2 (session_start();): Initializes or resumes a PHP session. It inspects incoming HTTP request headers for the PHPSESSID cookie. If absent, PHP generates a cryptographically secure 26-character pseudo-random session identifier, issues a Set-Cookie: PHPSESSID=...; path=/ HTTP response header, and allocates an internal session storage file (e.g., /tmp/sess_<id>). If present, it loads the serialized session data into the superglobal array $_SESSION.
    Execution Rule: Must be invoked prior to any byte of output (including UTF-8 BOM, whitespace, or HTML tags); otherwise, PHP raises an E_WARNING: session_start(): Session cannot be started after headers have already been sent.
  • Line 3 (require_once '../config/db.php';): File inclusion directive with absolute single-execution guarantee. Relative path ../config/db.php traverses one directory upward to include the database configuration. If the file is missing or contains fatal compile errors, require_once halts execution with an E_COMPILE_ERROR, preventing the script from running with an undefined database object $conn.
  • Lines 5–8 (if (isset($_SESSION['user_id'])) { header("Location: home.php"); exit(); }): Authenticated session guard.
    • isset($_SESSION['user_id']): Checks whether the primary key identifier of an authenticated user exists in the restored session superglobal.
    • header("Location: home.php");: Injects an HTTP/1.1 302 Found redirection header instructing the client browser to immediately dispatch a GET request to home.php.
    • exit();: Vital execution terminator. header() does not terminate script execution. Without exit(), the PHP interpreter would continue executing all downstream lines (9–83), leaking server-side computations, executing unauthenticated POST queries, and sending the login form in the response body despite the redirect header!

1. HTTP Statelessness & The PHP Session Mechanism:

The Hypertext Transfer Protocol (HTTP) is inherently stateless; each request across TCP is processed in complete isolation without built-in memory of prior requests. To construct an authenticated portal, state must be synthesized. PHP achieves this through session handling:

2. DOM Level 0 Form Navigation Hierarchy:

In accordance with the UCSC IS1207 syllabus specification, client-side script validation uses the classic DOM Level 0 object hierarchy: document.formName.inputName.value.

  • Why DOM Level 0 is Strictly In-Scope: The IS1207 examination explicitly examines candidates on navigating HTML forms using form names and element names as direct properties of the document object.
  • Why getElementById & Modern APIs Were Avoided: Using document.getElementById('username').value or document.querySelector('#username') introduces DOM Level 1/2 and Selectors API dependencies that bypass the specific hierarchical property traversal taught and examined in UCSC IS1207 past papers.
  • Why alert() Popups Are Used: Dynamic DOM modification (e.g. creating error spans with appendChild or modifying innerHTML) introduces asynchronous DOM manipulation outside the core syllabus scope. Synchronous modal alert() dialogs are the definitive IS1207 standard for user validation feedback.
UCSC IS1207 Past Paper Traps & Exam AlertsHigh-Frequency Exam Pitfalls
  • Trap 1: The Missing return Keyword in onsubmit (AY2020, AY2022):
    If written as <form onsubmit="checkLogin()">, the browser executes checkLogin(), evaluates it to false, but does not return that value to the submission handler. As a result, the form submits anyway despite invalid input! The syntax onsubmit="return checkLogin()" is mandatory to cancel submission.
  • Trap 2: Form name vs id Attribute Confusion:
    DOM Level 0 traversal (document.loginForm.username) relies strictly on the HTML name attribute. If a developer only defines <form id="loginForm">, document.loginForm evaluates to undefined, and attempting to read .username throws an uncaught TypeError: Cannot read properties of undefined, breaking form submission entirely.
  • Trap 3: Omitting exit() after header("Location: ..."):
    In PHP, sending a Location header does not kill the running process. If exit() is omitted after line 27, PHP continues processing lines 28–83 on the server, consuming CPU/memory and transmitting the entire HTML document body in the 302 redirect response.
  • Trap 4: String Equality == "" vs Strict Identity === "":
    In JavaScript, "" == 0 evaluates to true due to implicit type coercion. When validating text inputs, reading .value always produces a string primitive, so username == "" safely matches an empty string. However, understanding type coercion nuances is a favorite UCSC viva test.
Viva Question 1public/login.php: Line 2

Examiner: “Why must session_start() be placed at the very top of login.php before any HTML markup or whitespace?”

Candidate Model Answer:
Because session_start() operates by sending an HTTP response header (Set-Cookie: PHPSESSID=...). The HTTP protocol requires that all response headers precede any response body bytes. If even a single blank line, space, or HTML tag is emitted before line 2, PHP enters output buffering/streaming mode and issues an E_WARNING: Cannot send session cookie - headers already sent, resulting in broken session state and unauthenticated redirects.

Viva Question 2public/login.php: Line 43

Examiner: “What is the exact purpose of the return keyword in onsubmit="return checkLogin()"?”

Candidate Model Answer:
The onsubmit attribute is an inline event handler wrapper. When the user submits the form, the browser internally evaluates the attribute string as a function body. If we write onsubmit="checkLogin()", checkLogin() returns false, but the wrapper function itself returns undefined, allowing default form submission to proceed. Writing return checkLogin() ensures that the boolean value false is returned directly by the inline handler, instructing the browser's event dispatcher to call preventDefault() and abort submission.

Viva Question 3public/login.php: Line 19

Examiner: “How does your PDO prepared query protect against SQL Injection, and what would happen if you used string concatenation?”

Candidate Model Answer:
In line 19, $conn->prepare() sends the SQL statement with a parameter placeholder (?) to the MySQL database engine first. The query syntax and structure are parsed and compiled into an execution tree beforehand. When $stmt->execute([$username]) supplies user input, MySQL treats it strictly as passive literal data, never as executable SQL code. If we had used string concatenation (e.g., "SELECT ... WHERE username = '" . $username . "'"), an attacker entering admin' -- could manipulate the query AST, bypass password verification, and gain full unauthorized administrator access.

Viva Question 4public/login.php: Line 41

Examiner: “Why did you use addslashes($error) inside the alert(...) script tag?”

Candidate Model Answer:
If the $error message contains single or double quotation marks (for example: User's account disabled), echoing it raw into alert("<?php echo $error; ?>") would prematurely close the JavaScript string literal, producing an unhandled JavaScript SyntaxError (Uncaught SyntaxError: Unexpected identifier). addslashes() escapes quotes with backslashes, ensuring well-formed JavaScript literals and preventing reflected XSS.

function checkLogin() {
    var username = document.loginForm.username.value;
    var password = document.loginForm.password.value;

    if (username == "") {
        alert("Please enter your username.");
        return false;
    }

    if (username.length < 4) {
        alert("Username must be at least 4 characters long.");
        return false;

    if (username.indexOf(" ") !== -1) {
        alert("Username cannot contain spaces.");
        return false;
    }
    if (password == "") {
        alert("Please enter your password.");
        return false;
    }
    return true;
}
Technical Defense & Implementation Walkthrough:
To satisfy this challenge without using out-of-scope regular expressions:

  2. To forbid spaces without regex, we utilize the standard JavaScript string method username.indexOf(" ") !== -1. If a space character exists anywhere within the string, indexOf() returns an index greater than or equal to 0, triggering the alert and aborting submission.

UCSC IS1207 Past Paper Traps & Exam AlertsHigh-Frequency Exam Pitfalls
  • Trap 1: The Dual Empty Password Trap (pass != confirm):
    If a developer writes only if (pass != confirm), and the student submits both password fields completely blank, JavaScript evaluates "" != "" as false! The validation would pass! signup.php eliminates this trap with if (pass != confirm || confirm == "") combined with the preceding pass.length < 6 check.
  • Trap 2: JavaScript .length vs PHP strlen():
    In JavaScript, length is a property of the string object (syntax: pass.length). Writing pass.length() causes an unhandled TypeError: pass.length is not a function, breaking validation! In PHP, string length is calculated via the built-in function strlen($pass). Past paper questions frequently test this exact distinction between JS properties and PHP functions.
  • Trap 3: Using onclick on Submit Button vs onsubmit on Form:
    Attaching validation to <button onclick="return checkForm()"> only intercepts mouse clicks. If a user submits the form by pressing the Enter key inside an input field, the button's onclick event is completely bypassed, and unvalidated data is sent to the server! Form-level validation must always be bound to <form onsubmit="return checkForm()">.

UCSC IS1207 Past Paper Traps & Exam AlertsHigh-Frequency Exam Pitfalls
  • Trap 1: Checkbox HTTP POST Omission (AY2020, AY2021):
    When a user does not check a checkbox, the browser submits nothing for that input in the HTTP POST body. If code assumes the key exists (e.g. $t = $_POST['testimonial_checked'];), PHP throws an Undefined array key warning! Always use isset($_POST['testimonial_checked']) ? 1 : 0.
  • Trap 2: Checkbox Validation: .checked vs .value:
    In JavaScript DOM Level 0, document.appForm.testimonial_checked.value always evaluates to the string "on" whether the box is checked or unchecked! To evaluate whether the box is ticked, you must inspect the boolean property document.appForm.testimonial_checked.checked.
  • Trap 3: readonly vs disabled Form Field Behavior:
    An input marked disabled is excluded from the HTTP POST payload by the browser! If you mark the username field disabled, PHP receives NULL. To make a field visible and uneditable while preserving submission, you must use readonly.
  • Trap 4: Decimal Stepping in HTML5 Numeric Inputs:
    Standard <input type="number"> defaults to an integer step of 1. Entering 3.75 would trigger an HTML5 constraint validation error unless step="0.01" is explicitly specified!
