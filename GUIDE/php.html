1. Server Architecture & Apache vs. PHP Configuration Classification

Syllabus Theory Client vs Server Execution Lifecycle

PHP (Hypertext Preprocessor) is an open-source, server-side scripting language executed sequentially on the web server before any HTML is sent to the client browser:

Execution Metric Client-Side (JavaScript) Server-Side (PHP)
Runtime Environment Web Browser (V8, SpiderMonkey) Web Server (Apache HTTPD, Nginx)
Execution Trigger User events (clicks, input, hover) Incoming HTTP Request for .php file
Execution Flow Asynchronous / Event-driven Strictly sequential (top-to-bottom)
Source Code Visibility Viewable in browser source view Completely hidden; browser receives only rendered HTML/output
Past Paper Alert & Traps Guaranteed Q3 Exam Trap (AY21 & AY22)

Both semester exam papers (AY21 Q3.3 & AY22 Q3.III) present a list of directives and require you to classify whether they belong to Apache (httpd.conf) or PHP (php.ini):

Configuration Directive Target Configuration File Purpose & Operational Function
ServerRoot Apache (httpd.conf) Designates the top-level installation directory for Apache binaries, modules, and logs.
DocumentRoot Apache (httpd.conf) The filesystem root directory serving public web documents (e.g. /opt/lampp/htdocs).
LoadModule php_module Apache (httpd.conf) Instructs Apache to load the PHP interpreter shared object engine into memory.
PHPIniDir Apache (httpd.conf) Specifies the exact filesystem directory path where Apache must look for php.ini.
upload_max_filesize PHP (php.ini) Limits the maximum allowable byte size for an individual uploaded file (e.g. 3M).
post_max_size PHP (php.ini) Limits the total size of HTTP POST data submitted in a single request (default: 8M).
display_errors PHP (php.ini) Determines whether runtime errors/warnings are printed directly into HTML or kept internal.

2. Type Juggling, Operators (+ vs .) & Tracing Pitfalls

Syllabus Theory Dynamic Type Coercion

PHP is loosely typed and automatically converts types based on operational context:

  • Addition (+) vs Concatenation (.):
    • The + operator is strictly numerical. Strings are coerced to numbers: "5" + 10 evaluates to integer 15.
    • The . operator is strictly string concatenation: "5" . 10 evaluates to string "510".
  • Constants via define():
    • Constants are declared via define("x", "15"); and accessed as barewords without a dollar sign (x).
    • Variables are prefixed with $ ($x). x and $x are completely distinct entities!
  • Loose Equality Trap with in_array():
    • in_array("black", $colors) returns boolean false if not found.
    • Under loose comparison (==), false == 0 evaluates to true!
Past Paper Alert & Traps Recent Tracing Questions

Past Paper Question 1 (AY21 Q2.2.a):

define("x", "15");
$x = x + 10;
echo x;

// EXAM OUTPUT: 15
// Explanation: echo x prints constant 'x' (15). The variable $x (25) is ignored.

Past Paper Question 2 (AY22 Q3.II.a):

$x = "5"; $y = 10;
echo $x + $y . " ";
echo $x . $y;

// EXAM OUTPUT: 15 510

Past Paper Question 3 (AY22 Q3.II.c):

echo $x++ . " " . ++$x . " " . $x;

// EXAM OUTPUT: 5 7 7
// Explanation: $x++ prints 5 then increments to 6. ++$x increments to 7 and prints 7. Final $x is 7.

3. Array Mechanics, Key Casting & Auto-Indexing Rules

Syllabus Theory Indexed, Associative & Key Normalization

PHP arrays are ordered maps capable of holding mixed integer and string keys simultaneously:

  • Next Integer Index Auto-Assignment ($arr[] = val):
    When appending with empty brackets [], PHP automatically assigns an index equal to: $$\text{Current Maximum Integer Key} + 1$$ Even if lower integer slots are unoccupied, PHP never backfills!
  • String Key Casting to Integers:
    Strings containing valid decimal integer representations (e.g. "2", "12", "0") are automatically cast to standard integer keys!
    Result: An assignment to $arr["2"] will overwrite existing element $arr[2]!
Past Paper Alert & Traps High-Yield Array Tracing Questions

Past Paper Question 1 (AY21 Q2.2.d):

$arr = array(5 => 1, 12 => 2);
$arr[] = 56;
$arr["x"] = 42;
var_dump($arr);

// EXAM OUTPUT:
// array(4) {
//   [5]=> int(1)
//   [12]=> int(2)
//   [13]=> int(56)   <-- 12 + 1 = 13!
//   ["x"]=> int(42)
// }

Past Paper Question 2 (AY22 Q3.II.i):

$a = ["x" => 1, 2 => 2, 0 => 3, "2" => 4];
foreach ($a as $k => $v) {
    echo "($k:$v)";
}

// EXAM OUTPUT: (x:1)(2:4)(0:3)
// Explanation: "2" is cast to int 2, overwriting the value 2 with 4 while keeping its hash position!

4. The Foreach Reference Leak Gotcha (&$val)

Syllabus Theory Pass by Reference in Loops

When iterating over an array by reference using an ampersand (foreach ($arr as &$val)), each iteration assigns $val as a direct pointer reference to that array slot.

The Dangerous Reference Leak Trap:

When the loop concludes, the variable $val does not lose its reference! It remains permanently bound to the very last element of the array. Any subsequent modification to $val outside the loop will unintentionally overwrite the last element of your array!

Past Paper Alert & Traps AY22 Q3.II.f Exam Trap 
$nums = [1, 2, 3];
foreach ($nums as $n) { $n *= 2; }    // By value: $nums unmodified
foreach ($nums as &$n) { $n *= 2; }   // By reference: $nums is [2, 4, 6]
print_r($nums); echo "<br>";

$n = 100; // DANGER: $n is still a reference to the last element ($nums[2])!
print_r($nums);

<!-- EXACT EXAM OUTPUT -->
Array ( [0] => 2 [1] => 4 [2] => 6 ) <br>
Array ( [0] => 2 [1] => 4 [2] => 100 )

5. Superglobals, State Persistence & Session Lifecycle

Syllabus Theory $_GET vs $_POST vs $_SESSION

HTTP is a stateless protocol. PHP provides superglobals (automatically accessible across all scopes) to manage state:

  • $_GET: Data sent via URL query parameters (e.g. applications.php?view_sid=4&view_sch=1). Visible, bookmarkable, length-limited (~2KB). Never used for passwords.
  • $_POST: Data encapsulated within the HTTP request body. Invisible in browser bar, handles arbitrary binary data up to post_max_size.
  • $_SESSION: Server-side state store. Binds user state to a unique session identifier cookie (PHPSESSID) stored on client.
    • session_start(): Must be called at the very top of every PHP script before any HTML output is transmitted.
    • Write session: $_SESSION['role'] = 'admin';
    • Destroy session: session_unset(); session_destroy();
Codebase Implementation public/admin.php (Lines 1-8) & public/logout.php

In public/admin.php lines 1-8, we enforce Role-Based Access Control (RBAC) via session state:

1: <?php
2: session_start();
3: require_once '../config/db.php';
4: 
5: if (!isset($_SESSION['user_id']) || $_SESSION['role'] !== 'admin') {
6:     header("Location: home.php");
7:     exit();
8: }

In public/logout.php, we execute the full session destruction protocol:

1: <?php
2: session_start();
3: session_unset();
4: session_destroy();
5: header("Location: login.php");
6: exit();
7: ?>

6. File Inclusions & Modular Database Architecture (value.php + con.php)

Syllabus Theory include vs require Error Handling
Directive Behavior on Missing File Re-inclusion Safety
include Emits E_WARNING; script continues execution. May cause redeclaration errors if loaded multiple times.
require Emits E_COMPILE_ERROR; halts execution immediately. May cause redeclaration errors if loaded multiple times.
require_once Emits E_COMPILE_ERROR; halts execution immediately. Guarantees file is evaluated at most once per request lifecycle.
Past Paper Alert & Traps AY21 Q4.5/6 & AY22 Q4.II/III Exam Scenario

Both examination papers mandate establishing a modular database architecture separating credentials from connection logic:

<!-- FILE 1: con/data/value.php (Credentials) -->
<?php
$servername = "198.16.10.23";
$username = "root";
$password = "ucsc";
$dbname = "scholarship_db";
?>

<!-- FILE 2: con/con.php (Connection Engine) -->
<?php
require_once 'data/value.php';
$conn = new mysqli($servername, $username, $password, $dbname);
if ($conn->connect_error) {
    die("Connection failed: " . $conn->connect_error);
}
?>
Codebase Implementation config/db.php (Lines 1-14)

Our project implements this connection architecture using PDO with exception error handling:

1: <?php
2: $host = 'localhost';
3: $dbname = 'scholarship_db';
4: $user = 'root';
5: $pass = '';
6: 
7: try {
8:     $conn = new PDO("mysql:host=$host;dbname=$dbname;charset=utf8mb4", $user, $pass);
9:     $conn->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
10:     $conn->setAttribute(PDO::ATTR_DEFAULT_FETCH_MODE, PDO::FETCH_ASSOC);
11: } catch (PDOException $e) {
12:     die("Database connection failed: " . $e->getMessage());
13: }
14: ?>

7. Database Security: Prepared Statements & XSS Sanitization

Syllabus Theory SQL Injection & Cross-Site Scripting Immunity

Preventing SQL Injection with Parameterized Queries:

When user input is directly concatenated into SQL strings (WHERE user = '$name'), malicious SQL statements can alter execution logic. Prepared statements compile the SQL command structure on the database engine first, treating all incoming parameters strictly as passive data, rendering SQL injection mathematically impossible.

Preventing Cross-Site Scripting (XSS) with htmlspecialchars():

Reflecting unescaped database strings into HTML allows attackers to inject malicious <script> tags. htmlspecialchars($str) converts < to &lt;, > to &gt;, and & to &amp;, forcing the browser to render strings harmlessly as plain text.

Codebase Implementation public/admin.php (Lines 23-24) & public/login.php (Line 19)

In public/admin.php line 23, we execute a prepared insert:

23: $stmt = $conn->prepare("INSERT INTO users (username, password, email, role) VALUES (?, ?, ?, ?)");
24: if ($stmt->execute([$username, $password, $email, $role])) {
25:     $message = "User added successfully.";
26: }

And throughout our views, whenever database strings are printed to the browser, they are wrapped in htmlspecialchars():

<td><?php echo htmlspecialchars($u['username']); ?></td>
