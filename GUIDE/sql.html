1. Relational Theory, Key Hierarchy & 3NF Normalization

Syllabus Theory Database Concepts.pdf Curriculum

In relational database design (E.F. Codd, 1970), data is structured into two-dimensional relations (tables) governed by strict mathematical keys and integrity constraints:

  • Super Key: Any attribute combination that uniquely identifies a row.
  • Candidate Key: A minimal super key containing zero redundant attributes.
  • Primary Key: The chosen candidate key (enforces entity integrity: unique and never NULL).
  • Composite Primary Key: A primary key formed by combining two or more columns (e.g. student_scholarships(student_id, scholarship_id)).
  • Foreign Key: An attribute in a child table referencing a primary key in a parent table, enforcing referential integrity.

Database Normalization & Anomaly Elimination:

Normal Form Core Requirement Anomaly Eliminated
First Normal Form (1NF) All attributes must hold atomic values. No multivalued repeating groups (e.g. no comma-separated phone lists in a single cell). Eliminates repeating data groups and indexing ambiguity.
Second Normal Form (2NF) Must be in 1NF + No Partial Dependency. Every non-key column must depend on the entire candidate key, not a partial subset of a composite key. Eliminates update and deletion anomalies on composite entities.
Third Normal Form (3NF) Must be in 2NF + No Transitive Dependency. Non-key attributes must never depend on other non-key attributes ($X \to Y$ requires $X$ to be a super key). Eliminates insertion and update anomalies across independent entities.

In our project, we decomposed the system into 4 distinct, fully normalized 3NF relations:

  1. users (Primary Key: id): Holds authentication credentials (username, password, role, email).
  2. students (Primary Key: user_id referencing users.id): Holds extended applicant profile data. Satisfies 3NF because student bio data does not pollute the general authentication table.
  3. scholarships (Primary Key: id): Holds scholarship definitions (name, description, deadline).
  4. student_scholarships (Composite Primary Key: student_id, scholarship_id): A junction table resolving the Many-to-Many ($M:N$) relationship between students and scholarships.

2. DDL Schema Definition & Foreign Key Constraints

Syllabus Theory CREATE TABLE & Referential Actions

Data Definition Language (DDL) commands are auto-committed permanently by the database engine:

  • CREATE TABLE table_name (col datatype [constraints], ...);
  • Referential Actions on Delete:
    • ON DELETE CASCADE: Deleting the parent record automatically deletes all referencing child records.
    • ON DELETE SET NULL: Deleting the parent sets the child foreign key column to NULL.
    • ON DELETE RESTRICT / NO ACTION: Prevents deletion of the parent if any child records reference it.
  • TRUNCATE TABLE vs DELETE FROM (EXAM FAVORITE!):
    • TRUNCATE TABLE is DDL; it wipes the entire table, cannot be rolled back, and resets the AUTO_INCREMENT counter to 1.
    • DELETE FROM is DML; it deletes rows one-by-one, can be rolled back via transactions, and preserves the auto-increment counter.

3. DML CRUD Operations & Pattern Matching (LIKE)

Syllabus Theory SELECT, INSERT, UPDATE, DELETE

Data Manipulation Language (DML) manages table records:

  • INSERT INTO table (cols) VALUES (vals);
  • UPDATE table SET col = val WHERE condition; (Omitting WHERE updates all rows in the table!).
  • DELETE FROM table WHERE condition; (Omitting WHERE deletes all rows!).
  • Pattern Matching with LIKE:
    • %: Wildcard representing zero, one, or multiple arbitrary characters. E.g. WHERE name LIKE 'A%' (starts with A); LIKE '%tech%' (contains tech).
    • _: Wildcard representing exactly one single character. E.g. WHERE code LIKE '_D%' (second character is D).

4. Aggregate Functions, GROUP BY & The HAVING Rule

Syllabus Theory COUNT, SUM, AVG & Aggregates

Aggregate functions compute a single summary scalar value across a column of data:

  • COUNT(*): Returns total count of records including nulls.
  • COUNT(col): Returns count of non-null records.
  • SUM(col), AVG(col), MIN(col), MAX(col).
  • GROUP BY: Clusters rows with identical values into summary rows.
  • The Fundamental HAVING Rule (Slide 69):
    In SQL, the WHERE clause cannot filter on aggregate functions because WHERE filters individual records before aggregation takes place. The HAVING clause was introduced specifically to filter grouped summary records after aggregation! 
    -- WRONG (Syntax Error in SQL)
SELECT department, COUNT(*) FROM employees WHERE COUNT(*) > 5 GROUP BY department;

-- CORRECT RE-WRITE
SELECT department, COUNT(*) FROM employees GROUP BY department HAVING COUNT(*) > 5;

5. Relational Joins & Multi-Table Queries (INNER vs LEFT)

Syllabus Theory INNER JOIN vs LEFT OUTER JOIN

Relational joins synthesize attributes from two or more tables linked by foreign keys:

  • INNER JOIN: Returns rows only where an exact matching key exists in both tables. Unmatched rows are discarded.
  • LEFT JOIN (Left Outer Join): Returns all rows from the left table. If no match exists in the right table, columns from the right table evaluate to NULL.
  • The $N - 1$ Join Condition Rule: To join $N$ relational tables without triggering a Cartesian Product, you must specify at least $N - 1$ distinct join predicates (ON conditions).

SELECT items.item_id, items.item_name, suppliers.supplier_name
FROM items
INNER JOIN item_supplier ON items.item_id = item_supplier.item_id

In our project, line 41 of public/applications.php executes an enterprise 4-table relational join combining both INNER JOIN and LEFT JOIN:

41: $stmt = $conn->query("SELECT ss.*, u.username, u.email, st.full_name, st.name_with_initials, st.dob, st.gender, st.parents_income, st.parents_occupation, st.gpa, st.permanent_address, st.nic, st.contact_numbers, s.name AS scholarship_name

    INNER JOIN users u ON ss.student_id = u.id 
    LEFT JOIN students st ON u.id = st.user_id 
    INNER JOIN scholarships s ON ss.scholarship_id = s.id 
    ORDER BY ss.applied_at DESC");

Viva Code Defense: "We deliberately used a LEFT JOIN for the students table because if a student submitted an application before fully completing their optional profile details, an INNER JOIN would have completely hidden their application from the Registrar. The LEFT JOIN ensures the application remains visible even with partial profile data!"
